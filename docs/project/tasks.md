# 当前任务

最后更新：`2026-08-25`

本文件只维护**当前执行顺序**。已经成立的事实写入 [`state.md`](state.md)，稳定产品边界写入 [`spec.md`](spec.md)，阶段结构写入 [`plan.md`](plan.md)。

## P0：先把核心产品形态定下来

### 1. 论坛 / 图文内容形态

- [ ] 明确 Ruoshui 中“地点故事”的最终内容模型：标题、正文、照片、时间、地点等字段。
- [ ] 明确场景点位进入内容后的信息层级：地点页、代表故事、该地点全部故事之间如何组织。
- [ ] 明确 feed / detail 的图文展示方式，以及从内容返回 3D 场景的交互。
- [ ] 决定 v1 的发布边界；在登录、审核和反滥用能力完成前，不默认开放匿名 UGC。

### 2. 点位系统与点位 authoring

- [ ] 明确用户点击点位后的镜头运动、最终视角、内容出现方式和返回方式。
- [ ] 用真实点位替换当前无意义测试点位。
- [ ] 设计低摩擦的点位编辑流程，目标是“移动到目标视角 → 保存镜头 → 放置热点 → 绑定内容”，避免手填坐标和 camera 参数。
- [ ] 建立点位校准和验收流程。

### 3. 首批内容标准与照片筛选

- [ ] 选定首批约 5–10 个正式地点。
- [ ] 定义每个地点最低内容标准：封面、照片数量、正文、时间信息和地点关系。
- [ ] 对个人历史照片先按地点粗筛，再做精选，避免无目标处理完整照片库。

### 4. 照片上传与内容录入链路

- [ ] 跑通真实照片上传到 R2、业务数据写入 D1、页面读取展示的完整链路。
- [ ] 建立显式内容 seed / 管理流程，正常页面启动不得自动创建 scene、pin 或帖子。
- [ ] 让内容生产流程至少能稳定完成：筛选 → 分类 → 上传 → 填写 → 绑定点位 → 预览 → 发布。
- [ ] 补必要的图片类型、大小、上传确认与失败处理；完整 CMS 暂不要求。

## P1：核心内容链路成立后收口体验

### 5. 模型边界处理

- [ ] 为当前只覆盖校园主体区域的 3DGS 模型设计自然边界，避免用户看到突兀的空世界。
- [ ] 优先实验低成本方案：相机活动范围、远处雾化 / 天空融合、边缘弱化、低细节背景或镜头约束。
- [ ] 以“用户不明显感知模型被截断”为验收标准，不把补完整个周边城市模型设为前置条件。

### 6. 多设备支持

- [ ] 收口桌面端主体验。
- [ ] iPhone Safari 真机验证视口、安全区、横竖屏、热点点击、双指缩放 / 旋转和社区面板。
- [ ] 验证 Android Chrome 与 iPad / 触屏设备的核心链路。
- [ ] 根据真实设备表现处理移动端 GPU / 内存成本，而不是先做泛化性能优化。

### 7. 发布前测试

- [ ] 每个模块开发时持续做功能验证，不把测试全部留到最后。
- [ ] 做一次 release acceptance：首次访问、慢网、模型失败、API 失败、图片失败、点位跳转、内容浏览、返回场景和上传流程。
- [ ] 复验生产 Pages、`/api/*`、`/edge-models/*`、D1、R2 媒体链路。
- [ ] 找少量真实校友做可用性测试，重点观察是否能理解空间、发现地点故事并自然往返。

## P2：不阻塞 v1 的体验增强

### 8. Loading / Progressive SOG

- [ ] 先保留稳定、明确的 loading 反馈。
- [ ] 如需要提升体感，优先验证 tiny preview → full SOG。
- [ ] 只有前述方案明显不够时，再继续 incremental WebP / partial GPU upload 等重工程 PoC。
